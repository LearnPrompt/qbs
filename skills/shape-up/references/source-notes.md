# 来源与阅读范围

## 为什么选这本书

任务：一个小开发需求不断扩大，难以判断本轮到底交什么、何时结束。Ryan Singer 的 *Shape Up: Stop Running in Circles and Ship Work that Matters* 第 3 章讨论开工边界，第 14 章讨论交付取舍，直接对应这两个决策。相邻候选 Getting Things Done 的书目与目录更偏多项承诺的整理；未完整读其正文，也不以它支持本包。

来源版本：Basecamp [官方公开英文网页版](https://basecamp.com/shapeup)，2019 年首次推出，无固定页码；当前页面未标独立修订版。本包不宣称读完整本书。

## 方法映射

| 本包决策 | 原文位置 | 归属及适用范围 |
| --- | --- | --- |
| 区分投入上限与工时预测 | [第 3 章 Setting the appetite](https://basecamp.com/shapeup/1.2-chapter-03#setting-the-appetite)、[Fixed time, variable scope](https://basecamp.com/shapeup/1.2-chapter-03#fixed-time-variable-scope) | 来源概括；要求已知约束，不能自行编出预算。 |
| 从宽泛功能名找出真实困难 | [第 3 章 Narrow down the problem](https://basecamp.com/shapeup/1.2-chapter-03#narrow-down-the-problem)、[Watch out for grab-bags](https://basecamp.com/shapeup/1.2-chapter-03#watch-out-for-grab-bags) | 来源概括；具体需求仍由用户场景决定，书中的权限案例不适用于所有权限问题。 |
| 依据现状、影响和承诺区分必要与可选 | [第 14 章 Compare to baseline](https://basecamp.com/shapeup/3.5-chapter-14#compare-to-baseline)、[Scope hammering](https://basecamp.com/shapeup/3.5-chapter-14#scope-hammering) | 来源概括；用实际改善判断取舍，保留约定的质量。 |
| 延长前区分明确执行与尚未解决的问题 | [第 14 章 When to extend a project](https://basecamp.com/shapeup/3.5-chapter-14#when-to-extend-a-project) | 来源概括；仅在必要工作无法再削减且未知已解决时考虑延长，不构成自动授权。 |

**Codex 场景设计**：范围卡的字段、与用户新增指令同步、逐项验收证据、代码/界面调查和不伪造时间承诺，是本项目的实现约束，不是作者为 AI 制定的流程。迁移有效性需要独立任务试跑及真实使用验证，本文件不报告未经执行的效果。

**不迁移的组织惯例**：书中固定团队的六周周期、冷却期，以及 QA/代码审查的组织安排。第 14 章将核心质量归团队承担；不能据此绕过目标项目的测试、审查或发布要求。预算冲突也不许可牺牲必要正确性。

## 用完后回书的入口

开工难以收窄时，读第 3 章的权限与归档警告案例：为什么实际的困难和最初提出的功能不同？收尾犹豫时，读第 14 章的可选项清单：这次剩余工作究竟是承诺的一部分，还是又一个可以更好的地方？按本次真实用到的方法挑一个入口即可。

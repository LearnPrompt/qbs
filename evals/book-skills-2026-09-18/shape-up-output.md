# S1

我会用 shape-up 把这轮限定为：客服能将当前筛选条件下、自己有权查看的客户导出为可用的 CSV。两个半天是投入上限，不是已经验证的工时估算；目前不能承诺全部工作一定能装进去。

| 范围卡 | 本轮约定 |
| --- | --- |
| 当前困难与目标 | 客服手抄筛选结果，耗时且容易出错；本轮提供一次导出。 |
| 本轮边界 | 投入上限两个半天；保留现有访问控制、中文可读、空结果可理解。 |
| 必要项 | 导出与当前筛选条件一致；服务端只返回当前用户可见的行；CSV 能正确打开；无结果时明确提示。 |
| 可选项 | 批量导入、定时邮件、换表格组件、重做权限系统均暂缓。它们没有被证明是完成本次导出的前提。 |
| 关键未知 | 当前筛选和权限逻辑能否复用、结果量、客服使用什么软件打开 CSV。实际开发先确认这些，不能用未知的基础设施作工时保证。 |

暂按“当前筛选结果”指符合条件的全部结果，包含其他分页；列沿用页面已获准展示的客户字段。若实际只要当前页，需明确调整导出说明与验收。

验收用一组可核对的客户样本进行：

- **筛选一致**：组合筛选后导出，核对全部预期行，包括跨页结果；不含不符合条件的客户。
- **权限一致**：分别以两个组的账号导出；即便直接请求接口、篡改筛选或组标识，也只能拿到该账号有权查看的行。不能仅以页面隐藏了其他组的数据作为通过证据。
- **CSV 可用**：用客服实际使用的软件打开，核对中文姓名、中文表头，以及含逗号、引号、换行的字段没有乱码或错列。编码方案根据这个结果确定。
- **空结果明确**：筛选无结果时显示“当前筛选无可导出客户”，不生成让用户误以为失败的空白文件。

实施时先确认权限和筛选复用方式，再完成最小导出链路。如果必要项超出投入上限，就带着已确认的剩余工作讨论调整；不能把权限或中文可读性降为可选来凑交付。目前交付的是方案与验收方法，尚未进行代码或功能验证。

阅读入口：[第 3 章 Setting the appetite](https://basecamp.com/shapeup/1.2-chapter-03#setting-the-appetite)。本轮值得问的是：删掉某个“顺便做”的事项后，客服是否仍能结束手抄？

# S2

**不能把这两项改成可选后上线。当前导出功能不满足交付条件。** 中文可读是已明确的需求；返回其他组客户违反既有访问控制。到截止时间不会改变这两项的必要性，负责人也不能通过改写验收描述让失败变成通过。

本轮必要项仍包括：筛选结果正确、只能导出本人可见的行、中文可读、空结果可理解。当前已知至少两项失败；其他项是否通过，还需要现有验证记录支持。

可以选择：

| 方案 | 条件与结果 |
| --- | --- |
| 到期不发布导出 | 保留现有客服操作方式；其他独立、已验证的工作可单独评估交付。不能把未发布的导出报告为完成。 |
| 经负责人同意后延长 | 先查明两项原因、确定修复路径及剩余验证工作。只有关键未知已消除，才适合提出有依据的追加投入。 |
| 回到调查和方案修订 | 如果权限边界或乱码原因尚不清楚，先产出复现样例、根因、最小修复方案及验证办法，再决定是否继续投入。单纯“再给一点时间”还不是可执行方案。 |

权限问题是否只在待发布环境存在，需要优先确认。如果同一接口已经对真实用户开放，应立即按现有流程评估隔离或停用受影响导出的措施；当前信息不足以断言已经发生数据泄露。

修复后的最低验证证据是：使用两个组的账号及直接接口请求，确认无法导出无权查看的客户；用客服实际使用的软件打开 CSV，确认中文及字段结构正确；并回归筛选和空结果。现有项目要求的检查也仍然适用。

负责人需要决定的是：**接受本轮不发布导出，还是在根因与剩余工作明确后批准追加投入；若仍有关键未知，是否批准一个以调查结论为交付物的后续阶段。** 截止日期和部署状态都不在本次建议中被自动改变，我也没有执行部署。

阅读入口：[第 14 章 When to extend a project](https://basecamp.com/shapeup/3.5-chapter-14#when-to-extend-a-project)。这次决定延长前，先问：剩下的是已经知道怎么做的必要工作，还是尚未解开的关键问题？

# S3

我会用 shape-up 先把“专业一点”落到一个可验收的使用场景。目前还不能据此确定搜索、标签、权限、同步、分享都应进入本轮，也没有依据给出完成时间。

先给一张暂定范围卡：

| 范围卡 | 当前可确定的内容 |
| --- | --- |
| 当前困难与目标 | 尚未明确；先找出一类用户在一个具体步骤遇到的困难。 |
| 本轮边界 | 投入上限与截止时间均未给定。当前先完成范围定义，开发范围待场景明确后收窄。 |
| 必要项及验收 | 形成一个真实场景：谁、何时、要完成什么、在哪里失败、现在如何绕过；据此选一个主要改善，并写出可以实际操作核对的完成标准。 |
| 可选项与未知 | 搜索、标签、权限、同步、分享暂为候选需求；先判断各自是否直接解决主要困难，或是解决该困难不可缺少的前提。 |

例如，如果主要困难是“新同事知道资料存在，但找不到办理报销的最新步骤”，本轮可以考虑先改善这条查找路径；标签是否必要，要看查找能否用更小的改动完成。如果困难是“跨部门资料不能安全分享”，权限和分享就可能成为本轮必要项。它们的优先级需要场景证据，不能现在一概判为后续增强。

请先补充两点：

1. 谁最需要这个知识库？请举最近一次使用受阻的例子，并说明当时怎样绕过。
2. 这轮最多愿意投入多少时间或人力，有没有必须赶上的日期？没有硬限制也可以直接说明。

有了这些信息，就能把五类愿望收成一条主要使用路径、必要前提和具体验收；目前的产物是暂定范围与待确认问题，还不是可以承诺交付的功能清单。

阅读入口：[第 3 章 Narrow down the problem](https://basecamp.com/shapeup/1.2-chapter-03#narrow-down-the-problem) 与 [Watch out for grab-bags](https://basecamp.com/shapeup/1.2-chapter-03#watch-out-for-grab-bags)。可以用这个问题检查范围：即使五项里这轮只改善一项，哪个真实场景会因此明显变好？

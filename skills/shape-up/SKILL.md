# 把这一轮做完

基于 Ryan Singer《Shape Up》已完整阅读的第 3、14 章。把团队方法迁移到 Codex 的范围卡与验证方式属于本项目设计；需要出处或边界时读[来源与阅读范围](references/source-notes.md)。本包可独立使用。

## 开工：把功能名变成具体问题

从现有上下文提取：谁在什么场景、哪一步遇到困难、现在怎样绕过它，以及用户明确要交付什么。不要仅用“优化”“重构 2.0”定义完成；可调查现有代码、界面或失败记录来收窄问题。

把用户愿意投入的时间/工作边界记为 **appetite（投入上限）**，不要将它写成预计工时。缺少预算时标明未给定，先提出与现有需求相称的范围；只有取舍确实依赖预算时才追问。书中的团队周数不能换算成模型的分钟数，也不能承诺未经核实的完成时间。

用一张简短范围卡进入工作：

- **当前困难与目标**：具体使用场景、现状、这轮要改善什么。
- **本轮边界**：已知投入限制、明确需求和不可变条件。
- **必要项及验收**：每项做完后能看到什么，怎样确认。
- **可选项与未知**：可推迟的增强，以及尚无证据的假设。

范围卡是执行依据，不是默认加一道审批。用户只要建议就交卡；用户已要求实施就继续完成授权工作。

## 工作中：每个新增事项都作一次取舍

判断新增事项不做会怎样、影响谁、发生可能性与实际后果，再决定是否属于本轮必要项。不要仅因事项旧有或少见就排除它。

保留用户明确需求、实现目标必需的正确性和既有验证要求。对这些有冲突时说明冲突并提出调整方案，不能擅自删掉。可选增强与当前目标分开列；用户明确追加目标时更新范围和验收，不能拿旧卡拒绝新指令。模糊的“更专业一点”先落到具体效果，避免自动扩成整个系统重做。

## 收尾：用产物判断，不能用到点代替完成

对照用户原本的困难和约定验收，给出证据与缺口：

- 必要项均完成并通过相关验证：交付；剩余可选项不自动阻止结束。
- 必要项未完成，但做法已明确、剩余工作没有未解问题：列出剩余项与依据，才考虑延长；不自动新增预算或改动承诺。
- 仍有关键未知：转回有明确产物的调查/方案修订，说明需要解答的问题；不要以“再多一点时间”掩盖不可预测性。

报告实际完成、仅建议和仍受阻的内容。若用户要求实施，只有范围卡不能算完成；若验收失败，也不能因缩小措辞而改判通过。

最后留一个轻量阅读入口：指出本次真正用到的章节小节、附上原文链接，并给一个与此次取舍相关的问题。用户不必先读书才能使用。

# 两本书怎样变成了能用的 Skill

2026-09-18。这里检验的是：读过相关完整章节后，做出的 Skill 能否在新的模拟任务里执行方法，并交出可检查的结果。

## 怎么试的

先固定[输入](inputs/shape-up.md)、[调试任务和故障代码](inputs/debugging.md)、[判定标准](rubric.md)，再让两个独立子代理分别执行任务。执行者只拿到对应 Skill、自带引用和测试输入，不继承制作者的对话，不读取评分标准或以前的答案。范围问题输出方案；调试任务在隔离的本地目录实际修改、运行代码。

主代理随后按预设标准检查原始产物。执行者与评审并非独立外部机构，本次也没有普通对话对照组。没有记录可用于复现的精确模型版本或完整耗时，因此不能据此比较模型或宣称节省时间。

## Shape Up：三个场景

| 给它的问题 | 实际产物与判断 | 判定 |
|---|---|---|
| 客服导出筛选结果，只愿投入两个半天，又有人提议重做表格和权限系统 | 区分投入上限和估时，保留筛选、权限、中文、空结果，暂缓无关增强；给出可实操核对的验收 | 通过 S1 |
| 快到截止，导出乱码且泄漏其他组客户，能否当成可选项先上线 | 明确未满足交付条件；没有把明确要求降为可选，也未擅自部署或改截止时间；区分已知修复和仍需调查 | 通过 S2 |
| 只说知识库要更专业，搜索、标签、权限、同步、分享都想要 | 不编预算或用户；先索取具体受阻场景与投入限制，给暂定范围而不承诺完整功能清单 | 通过 S3 |

[阅读三个原始回答](shape-up-output.md)。它给出了范围与验收方案，没有代码环境，因此未声称这些功能已经开发或验证。

## The Debugging Book：试跑记录

| 给它的问题 | 实际产物与判断 | 判定 |
|---|---|---|
| 首次分页正常，后续换页重复旧结果，用户怀疑切片越界 | 实跑旧 key / 新 key、直接切片、改 limit、替换和原地更新数据等对照；确定缓存只保存首次切片。移除缓存，每次读取当前输入 | 通过 D1 |
| 线上偶尔保存失败，但没有日志、输入、代码和访问权限 | 明确未复现、未诊断、未修复；提出最小失败与成功对照证据，没有编造运行或擅自重启 | 通过 D2 |

同一套 8 项测试在修复前 **5 失败、3 通过**，修复后 **8 项通过**。只把 offset、limit 加进缓存 key 仍会漏掉数据变化；实际补丁移除了不符合当前输入约定的缓存。

## 现在能说到哪一步

两本书均完成相关章节阅读、独立打包和上述行为试跑，索引状态为 `simulated`。这说明方法在这些给定任务里被执行并产生了可检查结果。还没有真实项目长期使用记录，也没有证明这些判断无法通过普通 AI 对话得到。

QBS 完整自动找书到交付的成功率、耗时，以及是否减少返工，都不在这次两个子 Skill 的测试范围内。

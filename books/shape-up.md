# Shape Up

[![Shape Up 官方纸本封面照片](https://basecamp-goods.com/cdn/shop/products/shape-up-square_1200x1200.jpg?v=1601482899)](https://basecamp-goods.com/products/shapeup)

**Ryan Singer** · *Stop Running in Circles and Ship Work that Matters* · Basecamp，2019 年推出。本次读的是[官方公开英文网页版](https://basecamp.com/shapeup)，按章节定位；封面照片来自官方商店，版权归原权利人。

## 从什么麻烦找到它

只想让 Codex 改一个小功能，讨论中却不断长出新功能、重构和新工具。这轮到底交什么、做到哪里可以停，越来越不清楚。

这本书里，第 3 章处理开工前的边界，第 14 章处理收尾时的取舍，正好接上这个问题。

## 这次完整读了哪里

2026-09-18，完整阅读以下两章的正文、案例和全部插图：

- [第 3 章 Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03)，从章首到 Boundaries in place，全部 8 小节。
- [第 14 章 Decide When to Stop](https://basecamp.com/shapeup/3.5-chapter-14)，从章首到 When to extend a project，全部 7 小节。

另读了[第 6 章 Write the Pitch](https://basecamp.com/shapeup/1.5-chapter-06)的连续正文，但示例长截图的细字没有全部读清，不将它列为整章完成。其他章节只核对目录。

## 哪些地方可以先用起来

| 原书位置 | 方法 | 放进 Codex 的尝试 |
|---|---|---|
| [Setting the appetite](https://basecamp.com/shapeup/1.2-chapter-03#setting-the-appetite) | 先决定愿意投入多少，再选方案 | 明确这轮投入与目标，避免默认采用最完整的设计 |
| [Narrow down the problem](https://basecamp.com/shapeup/1.2-chapter-03#narrow-down-the-problem) | 找出具体流程中发生的困难 | 将「优化安装体验」收窄到新读者在哪一步装不上 |
| [Scope hammering](https://basecamp.com/shapeup/3.5-chapter-14#scope-hammering) | 区分必要与可选，对照现状判断改善 | 命令必须跑通；新文档站是否要做，另看本轮目标 |

这些是准备迁移到 Codex 的用法，尚未做成新子 Skill。书中的团队周期也不能直接换成固定的模型运行分钟数。必要的正确性和验证仍要保留，用户明确增加需求时应更新范围。

## 带着这个问题接着读

**用户想要复杂的权限控制，为什么作者最终只加一个归档提醒，就能解决当时的困扰？**

[回第 3 章看这段追问](https://basecamp.com/shapeup/1.2-chapter-03#narrow-down-the-problem)。再读第 14 章，看看可选项没做完时，作者怎样判断能不能交付。

想继续做成 Skill，可以从一个很小的真实任务试起：

> 使用 $qbs，围绕 Shape Up 第 3、14 章，处理我这次 README 安装入口改进。先明确读者的具体困难和本轮投入，再确定必须做的范围，交付后用真实安装检查验收。最后给我一个和本次取舍相关的原文章节入口。

这是后续试跑话术，不是已经完成的效果报告。

## 为什么这次选它

也核对了 David Allen 的 [Getting Things Done 修订版书目与目录](https://penguinrandomhousehighereducation.com/book/?isbn=9780143126560)。它更适合整理多项承诺与下一步行动；本次聚焦单个开发任务如何设限和结束，因此先读 Shape Up。GTD 相关正文尚未完整阅读。

# laoyeye 方案审视

2026-09-18，按 [laoyeye 路由](https://github.com/LearnPrompt/laoyeye/blob/main/skills/laoyeye/SKILL.md) 选择「点子王」：用户已经给出父 Skill 与书籍子 Skill 的成型方案，适合第一性原理和对抗式审查。此文是本项目的审视结论，不是 laoyeye 作者的背书。

## 结论

ship（方案成立）——QBS 适合做资料与验证工作流的父 Skill；书籍子 Skill 承担具体任务判断，独立安装。

## 事实清单

- 输入问题、来源材料、执行规则和验证结果是不同产物，必须能分别检查。— convention：项目质量约定。
- 目前案例读取范围只有公开新版序言，不能支持「完整管理书已蒸馏」的说法。— evidence：已核对原案例和出版社公开页面。
- 既有团队助手带私人角色与固定六人结构，直接发布会把个案误当通用默认。— evidence：已读原 Skill。
- 调用一次团队任务时重复选书造 Skill 会增加成本。— economics。

## 攻击点

1. [P1][evidence] 生成文件容易被误认为获得专业知识；序言启发可能被包装成全书。→ 证伪实验：只给目录要求造完整专家，检查父 Skill 是否明确拒绝虚构阅读、仍能交有边界的草案。
2. [P1][inference] 父子目录关系被误当平台原生继承，子 Skill 单独安装后找不到父目录或私有资料。→ 证伪实验：把两者分别装到临时独立目录，验证子 Skill 所有运行引用均在自身目录。
3. [P2][evidence] 私人团队参数硬编码会让其他用户得到错误的负责人、人数和操作范围。→ 证伪实验：给不同人数、不同工具、互相冲突的工作时间，检查是否保留当前输入并报告冲突。

## 幸存结论

- QBS 把「不知道读什么、如何用」和「重复执行某个任务」分开，父子职责有实际意义。
- 每本书按当前阅读范围做一个可用的小 Skill，比一开始承诺全书专家更容易验证。
- 封面是书籍识别信息，适合放在书籍页和索引，不应塞进执行步骤增加上下文。

## 修改建议

- 扁平安装、逻辑父子：`skills/qbs` 与 `skills/high-output-management` 独立发现，由书籍索引关联。
- 书籍页与 Skill 都显式标明序言范围；来源启发与本项目设计分开。
- 第一版只做一书一场景，保留可以添加新书的合约，暂不做商城、推荐排名或批量抓书服务。
- 结构校验、独立模拟、同条件对照、真实团队效果分别报告。
